## What to obtain first

Obtain a **Cardano Payment Service base URL and credentials**, not merely the hosted dashboard API key. The full Payment Service supplies purchasing/selling wallet custody, escrow actions, background transaction processing, and its own `/admin` interface. Official introduction explicitly identifies Payment Service as the component to run; current repository includes the dashboard and wallet-generation API. Hosted dashboard capabilities are investigated separately in `masumi-party-isolation.md`. [Introduction](https://www.masumi.network/dev/masumi/documentation), [repository README](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/README.md).

Ask organizers whether they supply full preprod Payment Service access. If they do, get its API version, supported Cardano payment-source types, purchasing-wallet provisioning, scoped credentials, native-token funding, refund operations, and ordinary transfer availability. If they do not, running the unmodified Masumi service is the documented route; Danila must approve deployment/hosting before implementation.

## Wallet roles required by our scenario

This is a proposed mapping of the agreed transaction flow, not a protocol requirement for separate dashboards:

| Party | Purchasing role | Selling role |
|---|---|---|
| NeoRack Consumer | Pays the three awards; receives award refunds | No seller listing required merely to purchase |
| TechBlog, CodePodcast, DevNewsletter | Pay bid fees and bonds; receive bond refunds | Receive awards |
| GamingForum | Pays bid fee | No award in rehearsed run; seller identity useful if genuinely bidding for future awards |
| Tender Board | Pays Validator | Receives bid fees and holds bonds |
| Validator | None in current flow | Receives verification fee |

Masumi's managed selling and purchasing wallets have different roles; optional external collection addresses can receive withdrawals. Owning several agents does not require several dashboards. Distinct party funds and authorizations are the real boundary. For a demo operated by one team, current full-service code supports several hot wallets per payment source and wallet-scoped API keys. This is shared custody by the operator, not independent ownership of signing keys by competing strangers. [Wallet concepts](https://www.masumi.network/dev/masumi/core-concepts/wallets), [wallet-import schema](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/payment-source-extended/schemas.ts), [API-key schema](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/api-key/schemas.ts).

## Step-by-step sequence

1. **Choose an existing preprod Cardano payment source and confirm version.** Read public `GET /payment-source` and the actual deployment's Swagger `/docs`. Use the deployed schemas, not copied examples from another release. The current source has both legacy V1 and V2; new seed defaults to V2. V2 seed has zero protocol fee, whereas older V1 documentation describes a 5% seller fee. This changes the Board's bid-fee-funded Validator economics. [Seed source](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/prisma/seed.ts).

2. **If self-hosting is approved, install the existing service unchanged.** Current README requires Node >=20, pnpm, PostgreSQL >=13; configure `DATABASE_URL`, `ENCRYPTION_KEY`, `BLOCKFROST_API_KEY_PREPROD`, and a private `ADMIN_KEY`, then migrate/seed/start according to that pinned release. Wallet mnemonics may be provided or generated during seed. Generated secrets must never reach our repo, browser, recordings, or tool output; inspect the chosen seed's output handling before running. Persist DB and encryption key. The service needs running background jobs, so its hosting is separate from short portal requests. [README](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/README.md), [configuration](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/docs/configuration.md).

3. **Provision just Consumer and TechBlog first.** In full service, `POST /wallet` with `network: Preprod` generates mnemonic/address/vKey but does **not** persist a managed wallet. Import into an existing payment source with admin-only `PATCH /payment-source-extended`, `AddPurchasingWallets` or `AddSellingWallets`; each entry contains mnemonic, note, and nullable collection address. Creating an entire new payment source is unnecessary merely to add another wallet. Safely handle mnemonics server-side; the agent needs API credentials and public wallet identifiers, not a seed phrase. [Generation handler](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/wallet/index.ts#L254), [import handler](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/payment-source-extended/index.ts#L296).

4. **Create limited credentials per participant.** Current key schema supports `canRead`, `canPay`, `canAdmin`, `NetworkLimit`, `walletScopeEnabled`, `WalletScopeHotWalletIds`; scope paying agents to their own wallets and Preprod. Avoid admin keys in agents. Non-admin refund requests also check that the requesting key owns the purchase record, so retain the purchasing key identity through the job lifecycle. [Key schema](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/api-key/schemas.ts), [refund authorization checks](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/purchases/request-refund/index.ts#L57).

5. **Fund test currency AND test ADA.** Consumer needs award currency; suppliers need fees/bonds currency; every signing wallet needs ADA for fees/output requirements. Confirm exact token policy + asset name and decimals against what organizers dispense and the registry quotes. Official Masumi listing guide documents tUSDM with six decimals; therefore 0.2 = 200000, 1.125 = 1125000, 0.375 = 375000 atomic units. Their top-up guide says ADA-only preprod, conflicting with their environment and registration guides. Availability of the correct tUSDM remains a practical funding check, not evidence that tUSDM is categorically unsupported. [Listing token table](https://www.masumi.network/dev/masumi/documentation/how-to-guides/list-agent-on-sokosumi), [environments](https://www.masumi.network/dev/masumi/core-concepts/environments), [conflicting top-up guide](https://www.masumi.network/dev/masumi/documentation/how-to-guides/top-up-your-wallets). Current Masumi code uses policy `16a55b2a349361ff88c03788f93e1e966e5d689605d044fef722ddde` and asset name `0014df10745553444d`; do not assume tokens with the same display name are interchangeable. [Token constants](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/frontend/src/lib/constants/defaultWallets.ts#L69).

6. **Register and exercise one reachable seller service.** TechBlog implements MIP-003; associate registration with its funded selling wallet and save `agentIdentifier`. Registration is on-chain and documentation estimates 5–15 minutes on preprod. Payment Service deployment does not deploy creative-generation agents. Dynamic pricing is needed for quotes that differ between jobs; current `/payment` supports `RequestedFunds` only for Dynamic pricing and requires `supportedPaymentSourceIndex` for V2. Board collects different fees and bonds, so do not register one fixed-price Board listing and assume it accepts arbitrary amounts. [Registration guide](https://www.masumi.network/dev/masumi/documentation/get-started/register-agent), [payment pricing checks](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/payments/index.ts#L241).

7. **Prove one successful job and one refund.** Seller `/start_job` prepares payment through seller-side `POST /payment`; buyer uses its own `POST /purchase`, preserving returned identifiers/timings, then polls until `FundsLocked`. Deliver off-chain result and submit hash using `POST /payment/submit-result`. Confirm actual withdrawal, not merely submitted result. For a cooperative refund, buyer calls `POST /purchase/request-refund` before unlock, seller calls `POST /payment/authorize-refund`, then confirm the buyer's collection. Use deployment-specific payloads and header (`token` in current full-service reference). [Payment lifecycle](https://www.masumi.network/dev/masumi/core-concepts/payments), [refund lifecycle](https://www.masumi.network/dev/masumi/core-concepts/refunds-and-disputes).

8. **Prove bond partial-return transfers and accounting.** Current full-service route table exposes admin-only **`POST /wallet/transfer-funds`**, with `fromWalletAddress`, `toAddress`, string `lovelaceAmount` and optional `assets[{unit, quantity}]`. Poll `GET /wallet/transfer-funds` for actual tx hash/status. Some code comments/tests still call it `/wallet/fund`; the route table is authoritative. Any managed hot wallet can supply transfers, including Board selling wallet. The endpoint requires **at least 2 ADA accompanying each transfer**, even native-token transfers. That ADA is sent to the recipient, not all consumed as a network fee. Track additional ADA separately from tUSDM commercial amounts. This transfer API is admin-only; admin credentials bypass wallet isolation, so a bidder cannot safely receive them. A privileged Board treasury backend is an architecture decision, not an established deployed capability. [Route table](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/index.ts#L345), [transfer handler](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/wallet/index.ts#L317), [transfer schema](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/wallet/schemas.ts).

9. **Expand participant wallets and register the other sellers only after those gates pass.** For the full agreed run, sellers are publishers, Board, and Validator; Consumer is a buyer. Preserve per-party wallet map, job ID, escrow purpose, token/amount, returned blockchain identifier, deadlines, hash references, transaction history, and confirmation evidence. Add idempotent job records before retrying financial operations.

## Full-flow feasibility and hidden dependencies

The 11 agreed escrow contracts are four bid fees, three awards, three bonds, one Validator fee. They are **not just 11 chain transactions**: creation, result submission, refund authorization, collection and batching each have their own actions. The worked example also needs three plain transfers: Board→CodePodcast 1.125 tUSDM; Board→Consumer 0.375; Board→Consumer 1.75. Those can be served by the existing full-service transfer API if that deployment has it; we have not executed them. [Agreed local flow](../../tender-flow.md), [full service routing](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/index.ts).

**Board cash flow must be explicit.** Bid fees and collected bonds arrive at the selling/return address. Validator purchases originate from a purchasing wallet; income does not automatically make that purchasing wallet spendable. Sweep selling→purchasing through existing transfer rails, choose supported return addresses, or pre-fund a treasury float and reconcile it. Do not silently claim the Validator is funded from locked bid fees before their collection. [Return-address defaults](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/purchases/schemas.ts#L346), [seller return-address default](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/payments/index.ts#L290).

**Board must submit bond-service result hashes in time** before collecting forfeited bonds. Holding money in escrow is not enough to withdraw as seller. TechBlog bond refund is supplier-buyer request plus Board-seller authorization. CodePodcast partial return is full Board bond collection followed by separate ordinary transfers; no native split-refund endpoint was found. [Seller lifecycle](https://www.masumi.network/dev/masumi/core-concepts/payments), [actual route table](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/index.ts).

**DevNewsletter no-result branch is slow.** Current `/payment` enforces submit-result deadline at least 15 minutes in the future, unlock at least 15 minutes after it, and external-dispute unlock at least another 15 minutes later. Current V2 service initiates automatic no-result refund only after submit-result deadline **plus 10 minutes**, then schedules chain collection. A refund request without a submitted result is also supported, but its mere submission is not collection. Seller-authorized refund removes the timed collection filter, but still requires transactions and polling. Fresh creation-through-settlement under 30 seconds is not supported by this tested source reading. Use actual pre-established/pre-recorded transactions with appropriate labels or show fresh operations pending; do not relabel requests as confirmed. [Deadline validation](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/src/routes/api/payments/index.ts#L145), [automatic no-result refund](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/packages/payment-source-v2/src/services/payments/automatic-decisions/service.ts#L99), [collection eligibility](https://github.com/masumi-network/masumi-payment-service/blob/d569a338ca54d5be7441564770d75ebf89b71f12/packages/payment-source-v2/src/services/purchases/collect-refund/service.ts#L1210).

Decision gates for Danila/Masumi mentor: deployment/custody model; available Cardano API/version; exact funded token; fee treatment; Board purchasing cash flow; privileged transfer backend; refund branch and demo timing. None requires building a wallet engine or smart contract.
